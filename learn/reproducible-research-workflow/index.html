可复现研究流程

可复现的意思是：别人拿到数据版本、代码、环境和说明后，能用一条命令重算出同一张表。代码能跑一次不算；可重算也不等于结论正确。

研究问题

一项月度分析有 36 个月度记录、其中 1 个月的数值缺失；作者删掉缺失月后保留 35 行，报告均值 4.2%、中位数 4.1%。另一位分析师用表格处理该缺失月，得到均值 4.3%；与作者相差 0.1 个百分点，但规则不可见。本文问：最小可复现流程包含什么，如何验证重算，又不能保证什么。数值为教学假设。

数据

假设一个原始文件只读、清洗与分析由脚本完成的小型月度项目。

产物 定义 单位 频率 期间 示例（假设） 许可
原始文件 只读观测，带来源和哈希 行 月 36 个月 36 行 × 3 列 不适用
清洗数据 按决策日志处理缺失 行 月 同期 35 行 不适用
代码与环境 脚本与依赖锁定 文件 每次运行 同期 1 脚本 + 1 锁文件 不适用
结果表 均值、中位数、样本量 % 或行 每次运行 同期 4.2 / 4.1 / 35 不适用

方法与假设

流程分获取、清洗、分析、验证、归档五步。获取时保存原始文件、来源、日期、许可和哈希，不覆盖原始文件；清洗用脚本处理缺失、异常值和变换，把每个删除、插补或改值决定写进决策日志，输出到独立目录；分析只读清洗数据并生成结果；验证检查行数、缺失率、汇总统计和预期输出，单元与端到端测试覆盖关键计算；归档固定代码、数据版本、依赖和运行命令。代码与文档纳入版本控制，数据与凭证不提交；记录系统、语言、包版本和随机种子；一条命令按序运行，合并前自动检查。关键假设：原始数据未改、脚本覆盖全部手工步骤、依赖可重建、输出有文档；任一不成立，“可复现”就只是“在我机器上跑过”。下面是本文整理的通用最小流程，不是本站数据管线的现状。本站快照记录输入文件的字节数、SHA-256 与取得时间，派生结果放在 data/snapshots/<快照日>/；缺值会让脚本报错，而不是写入决策日志。本站目前没有 run.sh，也没有覆盖数值计算的单元或端到端测试；现有检查针对登记一致性与页面行为。不要把这套清单当成“本站已经做到”。

结果

项目原始 36 行，清洗后 35 行；结果表均值 4.2%、中位数 4.1%、样本量 35。按 README 和锁文件在新环境重跑，输出与校验和一致，耗时约 12 秒。手工表格得到均值 4.3%，因为它对缺失月用了不同规则；代码没错，但规则不可见。可复现性来自数据、代码、环境、文档和验证的整条链。

稳健性

在干净环境重建并重跑；故意删除输入、改列名或改单位（单位与口径见数据单位与统计口径主文，RES-001），确认流程清晰报错而不是静默产出；用校验和比较输出；让未参与分析的人按 README 独立重跑。结果不一致时，先查数据版本、缺失规则、软件版本和舍入。失败条件：手工 Excel 修改、未记录筛选、发布后修订、依赖漂移与许可限制。

局限

可复现不等于正确：同一流程可稳定复现有偏样本、错误定义或错误模型。机密数据可能只能由受托人重跑，公开复现受许可限制。软件环境会失效，文档也可能漏步骤。数值为假设，不是真实项目。

复现

建议目录：data/raw/、data/clean/、src/、outputs/，根目录放 README.md、environment.lock 和 run.sh。README 记录来源、访问日期、许可、版本或哈希、运行命令、预期输出、时长和限制；run.sh 用一条命令完成清洗、分析、测试和校验；结果表带生成时间和哈希。

ONS 最佳实践指南把版本控制、测试、同行评审、数据管理与自动化列为可复现分析管道的组成部分：版本控制保存变更审计轨迹，测试验证代码按预期工作且可重复执行，同行评审检查分析是否适合用途，自动化在每次合并前运行测试[1]。

NIST 研究数据框架把可复现性定义为使用相同的工具与材料（文档化的元数据、代码与数据）重做同一分析[2]。

结论强度

记录完整的流程可让另一位分析师重算出同一张表，但不能证明样本代表性、方法正确或结论因果成立。“可复现”回答“能否重算”，“有效”回答“是否可信”，两者要分开。36/35 行、4.2%/4.1%/4.3% 和 12 秒均为教学假设。

知识点精读

API

定义：API 是程序访问数据服务的接口，规定端点、参数、认证、分页和速率限制。

机制：API 通过密钥、配额和格式约束访问数据；分页、重试和缓存影响完整性与成本，版本变更可能破坏管道。

例子：例如用 REST API 按日期和代码拉取行情，用 token 认证并处理分页。

边界：API 不是稳定数据库；限流、字段变更、停机和授权撤回会造成缺失，实时性和修订口径也不同，需记录调用和错误处理。

文件

定义：数据文件是本地或云端的结构化存储，如 CSV、JSON、Parquet、Excel 和数据库导出。

机制：格式影响类型、压缩、读取速度和 schema；编码、分隔符和嵌套结构会造成解析错误。

例子：例如 CSV 易读但类型丢失，Parquet 列式压缩适合大数据，JSON 适合嵌套。

边界：文件不是中性容器；编码、公式注入、隐藏行列和格式转换会改变数据，Excel 还会截断精度，需校验 schema 和编码。

清洗

定义：清洗是修正类型、重复、缺失、格式、单位和异常，使数据可用于分析。

机制：清洗包括标准化日期和代码、去重、缺失处理、单位换算和异常标记；规则应可复现并记录。

例子：例如把“1,234 元”转为数值 1234，统一股票代码和日期格式。

边界：清洗不是随意改数；过度清洗会删除真实极端，插补会制造信息，规则不一致会产生不可比数据，原始数据应保留。

校验

定义：校验是检查数据是否满足 schema、范围、唯一性、完整性和跨源一致性。

机制：校验规则包括类型、非空、主键唯一、数值范围和勾稽关系；失败应阻断或告警，而不是静默通过。

例子：例如检查价格非负、日期唯一、成交额与成交量乘价格大致一致。

边界：校验不是一次通过；规则过松会漏错，过严会阻断正常数据，跨源冲突需要优先级，校验也不能发现语义错误。

版本

定义：版本是记录数据、代码和配置在时间上的状态，支持复现、回滚和审计。

机制：版本可用快照、哈希、时间戳和版本库；point-in-time 数据还需记录修订和可得时点。

例子：例如保存每日行情快照和代码 commit，回测可复现同一结果。

边界：版本不是简单备份；存储成本、保留期和隐私会影响，覆盖写入会丢失历史，版本不一致会产生前视和不可复现。

自动更新

定义：自动更新是按计划或事件触发数据拉取、清洗、校验和入库，保持数据及时。

机制：更新需处理增量、幂等、失败重试、告警和回填；调度依赖数据发布日历和上游可用性。

例子：例如每日收盘后自动拉取行情，失败时告警并重试，缺失日回填。

边界：自动化不是无人值守；上游变更、时区和节假日会造成缺失，重复写入会污染数据，失败静默比停机更危险。

脚本

定义：脚本是把数据获取、清洗、分析和输出写成可重复运行的代码，带参数、日志和错误处理。

机制：脚本应幂等、可配置、记录输入输出和随机种子；版本控制和测试保证可复现。

例子：例如一个脚本按日期范围拉数据、清洗、生成报告，重复运行结果一致。

边界：脚本不是一次性代码；硬编码路径、隐式状态和缺失日志会使结果不可复现，随机性和外部依赖也会改变输出。

配置与依赖

定义：配置是脚本运行的外部参数，如路径、日期、API 密钥和模型参数；依赖是所需库、版本和系统环境。

机制：配置应与代码分离，密钥用环境变量或密钥管理，依赖用锁文件固定版本，环境用容器或虚拟环境复现。

例子：例如用 .env 存 API 密钥，用 lockfile 固定 pandas 版本。

边界：配置不是小事；硬编码密钥会泄露，依赖漂移会改变结果，环境差异和未固定版本会造成“在我机器上能跑”的问题。

数据与制度核对：可复现性

把“可复现性”放进真实数据之前，先核对四件事。第一是统计单位：来源报的是水平值、增长率、指数还是占比，分母是总产值、人口、劳动力还是金融资产；同一句话换掉分母就会得到不同结论。第二是时间口径：名义值与实际值、季调与非季调、财年与日历年不能直接拼接，涉及“版本控制”时尤其要写明基期和折算方法。

第三是制度边界。数据管理在来源国的法律、监管和会计规则下成立，换到另一套制度里，定义可能不覆盖同一批主体；跨境比较要先检查样本是否被同一规则约束。第四是反向核对：用另一个独立来源重算关键比例，至少让数量级、方向和单位对得上，再讨论因果。

边界条件与迁移练习：可复现性

学习“可复现性”最容易停在定义。真正要练的是把它和“版本控制”分开：前者回答哪个变量在动，后者回答这个变量通过什么渠道影响结果。两者经常同时出现，但一个描述状态，一个描述传导；把传导写成状态，就会把相关性误当因果。与“数据管理”的区别则在于层次：前者可以在单个主体上观察，后者要求一组共同规则约束同一批主体。三层混在一起，文章就会看起来什么都说了，实际什么都不能检验。

迁移练习的做法是换三个维度各问一次。换主体：从企业换到家庭，从银行换到基金，可复现性的分子分母是否仍然成立？换时间：从季度换到年度，从正常期换到危机期，参数是否稳定？换制度：从一套监管换到另一套，版本控制的激励是否方向相反？三次换完，仍能复述同一条机制，才算掌握；一换就崩，说明原来记住的是案例，不是概念。

最后做一次自测：用 100 字解释“可复现性”，必须包含一个单位、一个时间口径和一个反例；再用 100 字说明“版本控制”在什么条件下会失效。两段都写不出，就回到模块母文和同模块的另一篇主文，先把定义与口径对齐。模块深度不是字数，而是能否在换主体、换时间、换制度后仍给出可复核的判断。

练习

  1. 脚本每次运行都覆盖 data/raw.csv，有什么问题？应怎么改？
  2. README 至少应记录哪些内容，才能让别人重跑？
  3. 重跑的表与论文一致，但用了不同的缺失规则，这算可复现吗？应如何报告？
参考答案
  1. 原始数据应只读，脚本写入 data/clean/ 等派生目录并保存哈希；覆盖会破坏审计轨迹，也无法判断结果对应哪版数据。
  2. 来源、访问日期、许可、版本或哈希、依赖版本、运行命令、预期输出、时长和限制。
  3. 计算上可重复，但方法与文档不一致；应记录实际规则、说明差异，并重算与论文一致的结果。
  1. 用 100 字说明“RES-008”里的核心指标，必须写出分母和单位。
  2. 把“可复现性”与“版本控制”各写成一个可观察变量，并指出二者的时间差。
  3. 给“数据管理”找一个规则变化，说明它如何改变样本覆盖。
  4. 用本文的方法做一次反事实：只改变一个变量，其他条件保持不变。
  5. 如果换一个独立来源，哪一个数量级最可能变化？为什么？
  6. 写一条可证伪判断，包含观察信号、等待时间和复核指标。
