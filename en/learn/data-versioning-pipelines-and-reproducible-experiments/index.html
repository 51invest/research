Data Versioning, Pipelines and Reproducible Experiments

Reproduction is not rerunning a notebook; it means fixing data, code, environment and random seeds so every step is auditable.

ModuleRES-M12 · 数据工程与复现
LevelFoundation
Read7 min · 21 sections

Definition

A data version is an immutable identifier for the content and structure of data at a point in time, often a hash, snapshot or repository tag. A pipeline is an executable flow linking ingestion, validation, transformation, modelling and output. A reproducible experiment uses the same inputs, code, environment and random seed to obtain the same or explainable result. Raw data should be read-only, cleaned and derived data should be rebuildable, and outputs should carry a run record.

Intuition

Reproducing an experiment is cooking the same dish from a recipe: ingredient lots, heat, pans and order must be recorded, or you cannot explain why the taste changed. Data version is the ingredient lot, the code commit is the heat and steps, the runtime environment is the pan, and the random seed is the order of operations. Saving only the final report, without ingredients and steps, leaves no way to tell whether the recipe worked or the run happened to succeed. Reproducibility is not 'it runs again'; it is 'another person on another machine can reach the same conclusion from the record'.

Mechanism

A minimal pipeline has five stages: ingestion records source, time and checksum; validation checks schema, missingness, duplicates, ranges and units; transformation writes each step as a function and saves intermediate tables; modelling fixes random seeds and hyperparameters; output saves results, logs and an environment lock file. CI can rerun tests and a small sample on every commit, and data-drift monitoring compares distributions and key statistics. The audit record must answer which data, code version and environment produced the result [1][2].

Worked example

Suppose a monthly sales table has one million rows and the raw file hash is A; cleaning removes 2% duplicates and fills 0.5% missing values, producing derived hash B; the model output is C. If the supplier reissues the same month's file, the hash becomes A' even though only three rows differ, and the checksum flags the change. If the environment moves from Python 3.11 to 3.12, a floating-point library change can alter the last decimals; a lock file locates the difference. If the random seed is unfixed, cross-validation scores can move 0.3 percentage points, so a model 'improvement' cannot be judged. These are teaching examples.

Second worked example: data version and metric drift

Suppose a study trains on the September 2026 data version with 1,000 observations and gets AUC 0.80; the October version adds 100 observations, mostly new customers, and AUC falls to 0.78. Looking only at the final report suggests model decay; rerunning with the data version pinned shows AUC 0.80 on the old version, so the difference comes from sample composition, not code. If the default rate in the new sample rises from 5% to 8% while the threshold is unchanged, recall rises and precision falls; the model did not become better or worse, the distribution changed. The record must include the data hash, sample period, preprocessing version, random seed and metric definition; without any one, the 0.80-versus-0.78 gap cannot be explained. These are teaching assumptions.

Boundary and common mistakes

First, running once is not reproducibility: without fixed data and environment, another machine can differ. Second, hidden notebook state makes 'run all' disagree with current output; execute in order or use scripts. Third, when version control stores code but not large data, record snapshots and checksums separately. Fourth, licences and privacy may block sharing raw data; provide synthetic samples or access controls. Fifth, reproduction proves the result can be recomputed, not that the data are correct or the method valid.

Failure modes

The first failure is reproducing an old result with the latest data: once data updates, samples, features and labels change, so the result naturally differs. The second is relying on hidden notebook state: cells run in a different order, variables are overwritten, and a restart changes the answer; write the pipeline as a script that runs from scratch. The third is leaving seeds and environment unpinned: the same code can produce different results under different library versions or parallelism. The fourth is data leakage: using future information in preprocessing, or overlapping train and test sets, inflates metrics and cannot be reproduced. The fifth is recording only successes: deleted outliers, temporary parameter changes and abandoned models are part of understanding the result.

Three checks

First, is the data version uniquely identified by a hash or snapshot, with sample period and preprocessing fixed? Second, can the code rerun from an empty environment in one command, with seeds, dependency versions and parallelism recorded? Third, are metric definitions, test set and benchmark written down, and has leakage been checked? Only after all three can you speak of 'reproduction'; otherwise it is just 'it ran this time'.

Adjacent concepts and a counterexample

Reproducibility is easily confused with repeatability and replicability. Reproducible means the same team with the same data and code gets the same result; repeatable means another team with new data or a new experiment reaches a consistent conclusion; replicable means an independent study with the same design gets the same result. The evidence strength differs and they are not substitutes. A counterexample is 'the code runs, so it is reproducible': if the data version is unpinned, seeds unrecorded and dependencies drift, another machine gives a different result; running once is not reproducibility. Another is 'the same result means replication succeeded': if two studies share the same biased data, the same result only proves data alignment, not robustness. Distinguish data reproduction, code reproduction and conclusion replication, and record failures and deviations.

Scope and limits

This data-versioning and reproducibility framework applies to research with snapshotable data, lockable dependencies, recordable seeds and containerisable environments. If data cannot be shared under licence, experiments need specialised hardware, or results depend on live market state, full reproduction may be infeasible. It does not apply to treating a code repository as a data version, nor to proving robustness with one successful run. Pin the data snapshot and dependencies, record seeds and environment, and rerun in an independent directory; reproducibility is not replicability.

Finally, licence-restricted data should at least keep a synthetic sample and checksums so external researchers can reproduce the code path.

Research question

Data versions, pipelines and reproducible experiments ask “can the same research question produce the same result on another machine or another day?” If not, the conclusion is not stable evidence.

Data

Record raw data, retrieval time, version, cleaning rules, missing-value handling, sample filters and licence. Source revisions or definition changes must leave a difference record; do not overwrite the old version.

Method

Split retrieval, cleaning, features, modelling and evaluation into steps with inputs; record parameters, random seeds, dependency versions and output digests at each step. Identify versions by content hash, not filename.

Results

Report point estimates, intervals, sample sizes and failed runs together; reporting only successful runs hides selection bias. A reproducible experiment should rerun from raw data in a clean environment.

Robustness and limitations

Change time windows, samples, parameters and random seeds; check whether direction and magnitude hold. If results are sensitive to reasonable changes, state a conditional conclusion.

Reproduction checklist

Keep the environment lockfile, data version, scripts, parameters, random seeds and output hashes; have another person or machine rerun the checklist at least once.

Exercises

  1. Concept check: Concept check: why does a runnable notebook not prove reproducibility?
  2. Calculation: Calculation: one million raw rows, remove 2% duplicates and fill 0.5% missing values. About how many rows remain?
  3. Boundary: Boundary: when licensing limits data sharing, how can reproduction and privacy both be preserved?
Answer key
  1. Because data version, dependencies and random seeds are not fixed; hidden state, library versions and machine differences change results.
  2. Removing 20,000 leaves 980,000; filling missing values does not change row count, so about 980,000 remain if missing rows are kept.
  3. Provide synthetic samples, access controls, checksums and a remote execution environment; allow code and results to be checked without exposing raw data.
